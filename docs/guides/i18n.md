# Internationalisation (ADR-004 "Bharat-native")

Scope: `apps/web` (buyer site). Active languages (ADR-004): English (`en-IN`, default, unprefixed), Hindi `hi`, Kannada `kn`, Tamil `ta`, Telugu `te`, Marathi `mr`, Gujarati `gu`, Bengali `bn` (`/<code>/...`, tags `xx-IN`). All non-English catalogues are **machine-drafted and need native review** (`_meta` marker in each file).

## How it works

| Concern | Decision |
| --- | --- |
| Routing | Public discovery pages live in `src/app/[locale]/…`. `/` is English, `/hi/…` is Hindi. The proxy **rewrites** `/x` to `/en/x` internally and redirects an explicit `/en/x` to `/x` (308), so each language has exactly one URL. |
| Static rendering | `[locale]/layout.tsx` has `generateStaticParams` over the locales; server code always calls `getTranslations({ locale, namespace })` with the locale from params, never `useTranslations`/`headers()`/`cookies()`. Result: `/en`, `/hi`, `/kn`, …, `/<locale>/p/…` are `●` (SSG/ISR). A test (`test/i18n.test.tsx`) fails if `src/i18n` or `app/[locale]` import `next/headers`. |
| What next-intl is used for | Catalogue loading, ICU formatting (plurals), the client provider. Its middleware/routing/navigation modules are **not** used (they set cookies and headers that would defeat CDN caching). |
| Localised paths | `LOCALIZED_PREFIXES` in `src/i18n/config.ts` (search, categories, c/, s/, p/, products/, manufacturers, pricing, coming-soon/, home). Everything else (account, buyer, rfq, signin/signup, storefronts, APIs) is unprefixed English. `/hi/<not localised>` redirects to the unprefixed path. |
| Storefront hosts | Custom domains and `<slug>.<root>` subdomains are rewritten to `/store/<slug>` first and never see locale logic. |
| Language detection | **None on the server.** No redirect or cookie from `Accept-Language` (crawlers and shared links always get the requested URL; no `Set-Cookie` on cacheable responses). Instead, a page shows a dismissible client-side banner (written in the target language, with `lang`) when the first supported language in `navigator.languages` is not the page's language and is not English (`preferredLocale()` in `language-suggestion.tsx`; dismissal in `localStorage`). The choice lives in the URL. |
| `<html lang>` | Root layout renders `HtmlShell` (client) which reads `useSelectedLayoutSegment()`, so the prerendered HTML has `lang="<code>-IN"` on `/<code>/*` and `en-IN` elsewhere, without making the layout dynamic. |
| SEO | `localizedAlternates(path, locale)` (`src/lib/seo-i18n.ts`) gives a self-referencing canonical plus `hreflang` for all 8 locales (en-IN, hi-IN, kn-IN, ta-IN, te-IN, mr-IN, gu-IN, bn-IN) and x-default. Both `seo-i18n.ts` and the sitemap derive from `LOCALES`, so a new locale needs no edit there. Sitemaps add `xhtml:link` alternates per URL. JSON-LD `WebSite.inLanguage` per locale; product/seller/list URLs are locale-aware. |
| Fonts | `Noto Sans` per script via `next/font/google` in `src/app/layout.tsx`: Devanagari (Hindi + Marathi), Kannada, Tamil, Telugu, Gujarati, Bengali. Each is `preload: false`, `display: swap`, own subset; `@font-face` uses `unicode-range`, so a file downloads only when glyphs of that script render (English pages fetch none). All CSS variables sit in `--font-sans` (Geist for Latin, per-glyph fallback) and `:lang(hi\|mr\|kn\|ta\|te\|gu\|bn)` sets `line-height: 1.6` up front to avoid a reflow when the font swaps in. System fallbacks (Nirmala UI, Sangam MN, Kohinoor) are metric-close. |
| Numbers/dates | `formatNumber()` (`config.ts`) always uses `en-IN`: lakh/crore grouping and Latin digits (CLDR would give western grouping for kn/mr currency and native digits for bn/mr). `formatDate()` uses `LOCALE_META[l].intl` (`xx-IN-u-nu-latn`: localised month names, Latin digits). Time zone fixed to `Asia/Kolkata`. Note: a few call sites still use `toLocaleString(bcp47)` directly (e.g. the product price); prefer `formatNumber`. |
| Switcher | `src/i18n/language-switcher.tsx`: native `<select>` (all 8 locales, native names) with a visible `<label>`, `lang` on every `<option>`, `<noscript>` link fallback. In the header top bar, mobile menu and footer. Keeps path, query and hash; on non-localised pages it goes to the other language's home. |

## Files

- `messages/<code>.json` catalogues (nested by area; `_meta`/`_todo` keys are ignored) plus namespaced files `messages/<code>.<namespace>.json` (e.g. `en.ads.json`, `hi.promotions.json`). The loader (`src/i18n/messages.ts`) merges `<code>.json` then every `<code>.<ns>.json` in alphabetical namespace order (a file whose top level lacks a `<ns>` key is placed under `<ns>`), then deep-merges the result over the merged English, so a missing key falls back per key. Namespace files are found via a known list (`ads`, `promotions`) plus a directory scan of `messages/en.*.json`; add a name to `KNOWN_NAMESPACE_FILES` if a deployment does not ship `messages/` (the bundler only includes files matched by the import pattern). `test/i18n.test.tsx` requires every `en.<ns>.json` to have a complete mirror for all 7 other locales.
- `src/i18n/config.ts` locales, path helpers · `messages.ts` loader (deep-merge over English, client namespace list) · `request.ts` next-intl config · `link.tsx` `LocaleLink` · `html-shell.tsx` · `language-switcher.tsx` · `language-suggestion.tsx` · `server.ts` `resolveLocale`.
- `src/proxy.ts` `routeLocale()`.
- `@cnote/next-kit`: `labels` props on the auth forms (`AuthLabels`) and the unlock dialog (`UnlockLabels`); `@cnote/ui`: optional `labels` on `ProductCard`, `SellerCard`, `TrustBadge`, `Pagination`, `Breadcrumbs`, `WishlistButton`, `CompareToggle`. All default to English, so other apps are unaffected.

## Adding a language (e.g. Odia)

1. Create `messages/or.json` (+ `or.<ns>.json` for each namespaced English file); add a `_meta` header marking it machine-drafted.
2. `src/i18n/config.ts`: append to `LOCALES` and add a `LOCALE_META` entry (`L("or", "or_IN", "ଓଡ଼ିଆ", "odia")`; extend the `script` union).
3. Font: add the Noto family in `src/app/layout.tsx` (pattern of the others), its variable to `--font-sans` and the `:lang()` list in `globals.css`.
4. `next.config.ts`: add the code to the `:locale(...)` patterns; `test/i18n.test.tsx`: add the script regex to `SCRIPT_RE`; add a native banner string to `COPY` in `language-suggestion.tsx`.
5. `pnpm --filter @cnote/web typecheck && lint && test`, build, confirm `/or` and `/or/p/[slugId]` are `●`.

## Translation workflow

1. Add English first (`en.json`), using ICU for plurals/placeholders. No string concatenation; one message per sentence. Placeholders are `{name}`; plurals `{count, plural, one {# item} other {# items}}`.
2. Draft the translation (machine drafts are fine; keep the `_meta` marker until a native reviewer signs off).
3. Native review (below). Only then remove "machine-drafted" from `_meta`.
4. Catalogue data (category names, listing titles, seller names, review text) is **not** translated by this system; it is shown as authored. Do not put it in the catalogues.
5. Client components read only namespaces in `CLIENT_NAMESPACES` (`src/i18n/messages.ts`); add a new namespace there if a client component needs it.

## Review checklist (native reviewer)

- Natural, professional register for MSME buyers (आप, not तू/तुम); no literal word-for-word calques.
- B2B loanwords stay as people say them: कोटेशन, सप्लायर, ऑर्डर, MOQ (Latin), GST/KYC/HSN/SMS/WhatsApp (Latin).
- Consistency: one Hindi term per concept across the file (e.g. "सत्यापित" = verified, "भरोसा स्कोर" = trust score, "सेलर" for seller UI, "सप्लायर" for supplier).
- Placeholders intact and grammatical in context (`{title}`, `{seller}`, `{count}`); sentence still reads correctly for any value.
- Length: buttons and tabs are short enough not to wrap badly at 320px.
- Ranking promise ("never by payment") keeps its meaning; legal-ish copy (consent, privacy) matches the English intent exactly.
- No English left except allowlisted terms (the test flags it).
- Spot-check in the browser at `/hi`, `/hi/search?q=…`, a category and a product page, with a screen reader if possible (the language switcher options carry `lang`).

## Known gaps / follow-ups

- Private and transactional pages (sign-in/sign-up, RFQ, account, buyer, wishlist, compare) are English. Their components already read labels from the catalogue (`auth`, `rfq` namespaces, English provider); to localise them, move them under `[locale]` and make the proxy strip the locale prefix before `createAuthProxy` (protection and token refresh must still match `/rfq`, `/account`, …).
- Reviews and Q&A chrome, plan cards and the credit calculator on `/pricing`, server-action error messages and the storefront renderer are still English.
- The generated Open Graph image and its "Price on request" label are English (default `ImageResponse` fonts have no Devanagari).
- Product Open Graph image URLs use the internal `/en/p/…` path for English (works; not the pretty canonical URL).
- All six new-locale catalogues are machine-drafted: register, B2B terminology and plural phrasing need native review (checklist above, adapted per language). Each language should keep one term per concept.
- Build time and memory grow with locales × static params. If it becomes slow, limit `generateStaticParams` of the product/category pages for non-default locales to a top-N and rely on ISR (`dynamicParams` defaults to true) for the rest.
