# Internationalisation (ADR-004 "Bharat-native")

Scope: `apps/web` (buyer site). Active languages: English (`en-IN`, default, unprefixed) and Hindi (`hi-IN`, `/hi/...`).
Planned (catalogue stubs exist, not routable): Kannada `kn`, Tamil `ta`, Telugu `te`, Marathi `mr`, Gujarati `gu`, Bengali `bn`.

## How it works

| Concern | Decision |
| --- | --- |
| Routing | Public discovery pages live in `src/app/[locale]/…`. `/` is English, `/hi/…` is Hindi. The proxy **rewrites** `/x` to `/en/x` internally and redirects an explicit `/en/x` to `/x` (308), so each language has exactly one URL. |
| Static rendering | `[locale]/layout.tsx` has `generateStaticParams` over the locales; server code always calls `getTranslations({ locale, namespace })` with the locale from params, never `useTranslations`/`headers()`/`cookies()`. Result: `/en`, `/hi`, `/en/p/…`, `/hi/p/…` are `●` (SSG/ISR). A test (`test/i18n.test.tsx`) fails if `src/i18n` or `app/[locale]` import `next/headers`. |
| What next-intl is used for | Catalogue loading, ICU formatting (plurals), the client provider. Its middleware/routing/navigation modules are **not** used (they set cookies and headers that would defeat CDN caching). |
| Localised paths | `LOCALIZED_PREFIXES` in `src/i18n/config.ts` (search, categories, c/, s/, p/, products/, manufacturers, pricing, coming-soon/, home). Everything else (account, buyer, rfq, signin/signup, storefronts, APIs) is unprefixed English. `/hi/<not localised>` redirects to the unprefixed path. |
| Storefront hosts | Custom domains and `<slug>.<root>` subdomains are rewritten to `/store/<slug>` first and never see locale logic. |
| Language detection | **None on the server.** No redirect or cookie from `Accept-Language` (crawlers and shared links always get the requested URL; no `Set-Cookie` on cacheable responses). Instead, an English page shows a dismissible client-side banner "हिंदी में देखें" when `navigator.languages` prefers Hindi (dismissal in `localStorage`). The choice lives in the URL. |
| `<html lang>` | Root layout renders `HtmlShell` (client) which reads `useSelectedLayoutSegment()`, so the prerendered HTML has `lang="hi-IN"` on `/hi/*` and `en-IN` elsewhere, without making the layout dynamic. |
| SEO | `localizedAlternates(path, locale)` (`src/lib/seo-i18n.ts`) gives a self-referencing canonical plus `hreflang` en-IN, hi-IN and x-default. Sitemaps add `xhtml:link` alternates per URL. JSON-LD `WebSite.inLanguage` per locale; product/seller/list URLs are locale-aware. |
| Fonts | `Noto Sans Devanagari` via `next/font/google`, `preload: false`, `display: swap`, subset `devanagari`. `@font-face` uses `unicode-range`, so the file downloads only when Devanagari text renders. Font stack falls back per glyph (Geist for Latin). `:lang(hi)` sets `line-height: 1.6` up front to avoid a reflow when the font swaps in. |
| Numbers/dates | `Intl` with `hi-IN`/`en-IN` (Indian digit grouping, Latin digits). Time zone fixed to `Asia/Kolkata`. |
| Switcher | `src/i18n/language-switcher.tsx`: native `<select>` with a visible `<label>`, `lang` on every `<option>`, `<noscript>` link fallback. In the header top bar, mobile menu and footer. Keeps path, query and hash; on non-localised pages it goes to the other language's home. |

## Files

- `messages/<code>.json` catalogues (nested by area; `_meta`/`_todo` keys are ignored).
- `src/i18n/config.ts` locales, path helpers · `messages.ts` loader (deep-merge over English, client namespace list) · `request.ts` next-intl config · `link.tsx` `LocaleLink` · `html-shell.tsx` · `language-switcher.tsx` · `language-suggestion.tsx` · `server.ts` `resolveLocale`.
- `src/proxy.ts` `routeLocale()`.
- `@cnote/next-kit`: `labels` props on the auth forms (`AuthLabels`) and the unlock dialog (`UnlockLabels`); `@cnote/ui`: optional `labels` on `ProductCard`, `SellerCard`, `TrustBadge`, `Pagination`, `Breadcrumbs`, `WishlistButton`, `CompareToggle`. All default to English, so other apps are unaffected.

## Adding a language (e.g. Kannada)

1. Translate `messages/kn.json`: copy the structure of `en.json` (any key you omit falls back to English at runtime). Add a header key `"_meta": "Kannada (kn-IN). MACHINE-DRAFTED, NEEDS NATIVE REVIEW …"` if machine drafted.
2. `src/i18n/config.ts`: move `"kn"` from `PLANNED_LOCALES` to `LOCALES`, add its `LOCALE_META` entry (`bcp47: "kn-IN"`, `hreflang`, `ogLocale: "kn_IN"`, native name in its script).
3. Font: add the script's Noto family in `src/app/layout.tsx` (same pattern as Devanagari: `preload: false`, subset), append its variable to `--font-sans` in `globals.css`, and add its class variable to `HtmlShell`'s `className`.
4. `next.config.ts`: the `/hi/...` cache and redirect rules and the `:locale(en|hi)` og-image rule are per locale; add the new code (or generalise the source pattern).
5. `test/i18n.test.tsx`: it iterates `LOCALES`; add the parity/untranslated checks for the new catalogue (copy the `hi` blocks), update the `LATIN_OK` set if needed. Numerals and grouping come from `Intl`.
6. Run `pnpm --filter @cnote/web typecheck && lint && test`, then build and confirm `/kn`, `/kn/p/[slugId]` are `●`.

## Translation workflow

1. Add English first (`en.json`), using ICU for plurals/placeholders. No string concatenation; one message per sentence. Placeholders are `{name}`; plurals `{count, plural, one {# item} other {# items}}`.
2. Draft the translation (machine drafts are fine; keep the `_meta` marker until a native reviewer signs off).
3. Native review (below). Only then remove "machine-drafted" from `_meta`.
4. Catalogue data (category names, listing titles, seller names, review text) is **not** translated by this system; it is shown as authored. Do not put it in the catalogues.
5. Client components read only namespaces in `CLIENT_NAMESPACES` (`src/i18n/messages.ts`); add a new namespace there if a client component needs it.

## Review checklist (native reviewer)

- Natural, professional register for MSME buyers (आप, not तू/तुम); no literal word-for-word calques.
- B2B loanwords stay as people say them: कोटेशन, सप्लायर, ऑर्डर, MOQ (Latin), GST/KYC/HSN/SMS/WhatsApp (Latin).
- Consistency: one Hindi term per concept across the file (e.g. "सत्यापित" = verified, "भरोसा स्कोर" = trust score, "सेलर" for seller UI, "सप्लायर" for supplier).
- Placeholders intact and grammatical in context (`{title}`, `{seller}`, `{count}`); sentence still reads correctly for any value.
- Length: buttons and tabs are short enough not to wrap badly at 320px.
- Ranking promise ("never by payment") keeps its meaning; legal-ish copy (consent, privacy) matches the English intent exactly.
- No English left except allowlisted terms (the test flags it).
- Spot-check in the browser at `/hi`, `/hi/search?q=…`, a category and a product page, with a screen reader if possible (the language switcher options carry `lang`).

## Known gaps / follow-ups

- Private and transactional pages (sign-in/sign-up, RFQ, account, buyer, wishlist, compare) are English. Their components already read labels from the catalogue (`auth`, `rfq` namespaces, English provider); to localise them, move them under `[locale]` and make the proxy strip the locale prefix before `createAuthProxy` (protection and token refresh must still match `/rfq`, `/account`, …).
- Reviews and Q&A chrome, plan cards and the credit calculator on `/pricing`, server-action error messages and the storefront renderer are still English.
- The generated Open Graph image and its "Price on request" label are English (default `ImageResponse` fonts have no Devanagari).
- Product Open Graph image URLs use the internal `/en/p/…` path for English (works; not the pretty canonical URL).
