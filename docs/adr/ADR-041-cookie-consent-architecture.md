# ADR-041: Cookie consent architecture: per-app registries, policy snapshots, receipts without IP

**Status:** Accepted (records decisions already implemented in PRs #11, #17, #24, #32; detail in `docs/design/cookie-consent.md`)
**Note:** Implements ADR-010 (DPDP) and ADR-004 (Bharat-native UX). Supplements ADR-039, which gates Clarity on analytics consent.

**Context.** Before this work the buyer web wrote non-essential storage (visitor id, ad-click attribution, lead-gen nudge history) without asking, and the only banner was a binary analytics prompt that rendered only when Clarity was configured. DPDP Act 2023 s.6 requires specific, informed, withdrawable consent and puts the burden of proof on the data fiduciary (s.6(10)); the same behaviour is the GDPR/ePrivacy standard. The platform has four separately hosted Next apps (cookies are host-scoped), storefronts rendered by the buyer web under custom domains, and a plan to embed third-party video and maps in storefronts.

**Options.**
1. One binary "analytics" banner on the buyer web; other apps ignore the issue.
2. A third-party consent-management platform.
3. A first-party consent manager: one framework-free core package, a per-app registry of every storage key, committed policy snapshots, server-side receipts, and a gate component for third-party embeds.

**Decision.** Option 3.
- **Categories.** `necessary` (always on, no consent: sign-in, security and things the user explicitly asked for or dismissed), and three opt-in categories, none pre-ticked: `analytics`, `marketing` (visitor id, attribution, lead-gen nudges, sponsored click attribution) and `functional` ("Preferences and personalisation", e.g. the Recently viewed rail). `functional` is its own purpose and is not bundled into marketing (DPDP s.6 specificity). "Reject all" sits on the first layer with equal prominence to "Accept all"; no cookie wall.
- **Registry is the single source of truth.** Each app lists every cookie, localStorage and sessionStorage key with category, provider, purpose and duration (`apps/web/src/features/consent/registry.ts`, `apps/seller/src/features/consent/registry.ts`). The preferences dialog, the cookie policy page and withdrawal cleanup read it. Tests fail when source mentions an unregistered `cnote_*` key; an e2e runtime audit (`e2e/a11y/cookie-audit.spec.ts`) fails when the browser holds a key that is not registered or anything non-necessary exists before opt-in.
- **Shared core, per-app state.** `@cnote/consent` is a leaf package with no dependencies (record format, registry helpers, GPC, receipt outbox, withdrawal cleanup, snapshot hashing, test scanners). The React banner/dialog is `@cnote/next-kit/consent` and the shared `POST /api/consent` handler is `@cnote/next-kit/consent-route` (receipt writer injected, because `@cnote/compliance` sits above next-kit). Each app has its own cookie (`cnote_consent`, `seller_consent`), registry, policy version and snapshots. The seller app has optional storage (onboarding timing, referral code) and gets a banner. **Admin and studio hold only strictly necessary storage: no banner, but a registry and a test (`auditNecessaryOnlyApp`) that fails the day optional storage, a third-party script or iframe, or Sentry replay/tracing appears.** Storefronts are rendered by the buyer web and inherit its banner and gating.
- **Policy versions and snapshots.** `CONSENT_POLICY_VERSION` (+ `CONSENT_POLICY_UPDATED`) is bumped whenever the registry or a notice string changes. A choice recorded at an older version means "no choice": everyone is asked again. Every shipped version has a committed `policy-snapshots/v<N>.json` (full registry plus en/hi notice strings, canonical JSON); a test compares it with the live registry and strings. Older snapshots are never edited. The receipt's `registry_hash` is the sha256 of the snapshot, so years later we can show exactly what the visitor saw. Choices expire after 12 months.
- **Receipts.** `POST /api/consent` appends a `CookieConsentReceipt` (`consent_id`, `policy_version`, per-category choice, `gpc`, `action`, `locale`, nullable `person_id`, the browser's `client_at`, `registry_hash`, and `app`, which the server sets and the browser cannot send). **No IP address and no user agent are stored**; the IP is only the rate-limit key. The endpoint is idempotent on `(consent_id, client_at)`, and the browser keeps unacknowledged receipts in `cnote_consent_pending` (registered strictly necessary) and resends until it gets a 200. Retention is 3 years, then purged (inside `withPurge`, ADR-042). Erasure sets `person_id` to NULL and keeps the anonymous proof; that is the one deliberate exception to append-only. Visitors can download their own record by consent ID.
- **Global Privacy Control** (`navigator.globalPrivacyControl` or `Sec-GPC: 1`) turns marketing off by default and is recorded on the receipt; it never affects `functional`. Do Not Track is not honoured. Same opt-in behaviour everywhere, no geo variants.
- **Account sync (buyer web).** For signed-in people the choice is mirrored into the identity consent ledger (`analytics_cookies`, `marketing_cookies`, `functional_cookies`), and the newer of cookie and ledger wins per purpose on load.
- **Third-party embeds.** `<ConsentGate category provider>` renders an accessible placeholder and does not create the children (no iframe, no request, no IP disclosure) until the category is granted or the visitor chooses "Load it" for that one item. A test enforces that iframes sit inside the gate. The web CSP `frame-src` lists exactly `youtube-nocookie.com` and `openstreetmap.org` (plus Turnstile when configured).
- **Embeds ship dark.** The storefront `embed` block is behind `STOREFRONT_EMBEDS_ENABLED` (default off) because its content is not yet moderated (ADR-003). Off: Studio hides the block, saving or publishing a document with one is rejected, a stored one renders nothing, and the web notice stays at policy v3. On: the notice gains the embeds sentence (v4, snapshot `v4.json`) and everyone is asked again. The flag is inlined at web build time, so changing it needs a rebuild.
- **DPDP rights requests** reuse the grievance flow: request types (access, correction, erasure, nomination, withdraw_consent) with a 90-day SLA; staff review them in `/compliance/consent` (privilege `compliance.consent`, every search and export audited).

**Rationale.**
- The burden of proof (s.6(10)) is met by what we store: a per-version snapshot, a hash on every receipt and a timestamped choice, with no extra personal data.
- A registry plus tests turns "did someone add a tracker?" into a failing build instead of a review comment, in every app including the ones with no banner.
- Splitting the core from the UI keeps admin, studio, compliance and the snapshot tooling free of Next (ADR-006).
- Re-asking on every notice change is the safe default for proof, at the cost of some fatigue.

**Consequences.**
- Adding or renaming any storage key is a three-part change: registry entry, translations in all catalogues, and a policy version bump with a new snapshot. This is deliberate friction.
- Web policy snapshots exist for v1, v3 and v4 (`POLICY_SNAPSHOTS` in `apps/web/src/features/consent/policy.ts`); the seller app has v1.
- Receipts of the seller app are per device and are not mirrored into the identity ledger.
- The seller app has no cookie-policy page; its banner points to the preferences dialog. Native review of the six non-live catalogues is still open.
- Turning on embeds requires moderation of the embedded video title (follow-up in the design doc) and a web rebuild.
- Google Consent Mode and IAB TCF are not applicable until a Google tag or programmatic advertising exists; the design doc records the mapping to use then.

**Review.** At every notice or registry change, and before `STOREFRONT_EMBEDS_ENABLED` is turned on. Counsel to confirm the 3-year receipt retention and the erasure exception.
