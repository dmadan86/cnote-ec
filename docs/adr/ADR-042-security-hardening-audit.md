# ADR-042: Security hardening after the audit: fail closed, enforce in the database, validate at startup

**Status:** Accepted (records decisions already implemented in PRs #35, #36, #37, #38; control-by-control detail in `docs/security/security-architecture.md` sections 5, 5a, 6a, 8 to 12)
**Note:** Extends ADR-037 (security layers), ADR-029 (auth realms, MFA), ADR-008 (AI orchestration) and ADR-010 (compliance).

**Context.** A security audit of the Phase-1 build found controls that depended on convention or on a correct deployment: append-only ledgers enforced only in application code, forgeable partner webhooks (built-in default secrets, mock partners reachable in production), a client-IP rule that trusted a spoofable header, OTP codes echoed in responses, prompt injection able to flip a moderation verdict, and a production boot that accepted missing or weak configuration. The findings were labelled H1 to H4 (high) and M1 to M10 (medium).

**Options.**
1. Fix each finding in place and document it.
2. Rely on deployment checklists and reviews.
3. Fail closed by default, move invariants into the database and the process start-up, and keep a regression test per control.

**Decision.** Option 3. The decisions that need to outlive the individual fixes:

1. **Webhooks fail closed (H1, M7).** There are no built-in webhook secrets; an unset `ESCROW_WEBHOOK_SECRET` or `CREDIT_WEBHOOK_SECRET` means nothing verifies. Escrow and credit webhooks refuse while the feature flag is off (events that settle existing obligations from the configured partner are still accepted so money in flight is never stranded), accept only the configured partner, and refuse the `mock` partner under `NODE_ENV=production` unless the e2e-only `ESCROW_MOCK_CHECKOUT` / `CREDIT_MOCK_CHECKOUT` is set. The payments mock gateway is allowed only in development and test (or the guarded `PAYMENTS_ALLOW_MOCK_IN_PRODUCTION`, ignored next to a real gateway). A paid outcome needs a verifiable amount and a matching provider. Every webhook route reads a capped stream. Only the buyer's own `won` report creates an Order; a seller's is advisory.
2. **Append-only is a database guarantee (M5).** `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers (migration `20261003000000_append_only_triggers`) protect `admin_audit_log`, `credit_ledger`, `ad_wallet_ledger`, `consents`, `ledger_journals`, `ledger_lines`, `domain_events` (only `published_at` may change, for the relay) and `cookie_consent_receipts` (only `person_id` to NULL, for erasure). A retention purge opts in per transaction with `withPurge(tx => ...)` from `@cnote/db`, which sets the transaction-local `cnote.allow_purge`. Test and e2e databases default the setting on (`scripts/allow-test-purge.sh`) so suite cleanup works; `UPDATE` is never bypassed. The triggers are raw SQL that `prisma migrate diff` ignores, so `db:new` neither drops nor needs to strip them. The setting guards against mistakes, not against someone who can run arbitrary SQL as the owning role; `docs/ops/db-roles.md` describes the optional least-privilege role for that.
3. **Production start-up validation (M8).** `validateSecrets` / `assertRequiredSecrets` (`packages/security/src/secrets.ts`) run at boot of every app and the worker and throw in production on: weak or missing JWT secrets and realm-secret reuse, missing or malformed field-encryption and blind-index keys, missing `DATABASE_URL` / `REDIS_URL`, Postgres without TLS and Redis without `rediss://` (explicit waivers `DB_TLS_OPTIONAL`, `REDIS_TLS_OPTIONAL` for documented private networks), `OTP_DEV_ECHO`, a missing webhook secret for any enabled provider, `REVALIDATE_SECRET` under 32 characters, `DOMAIN_CHECK_SECRET` missing with custom domains on, `CSP_REPORT_ONLY=1` without `CSP_REPORT_ONLY_ACK=1`, and missing Turnstile keys. `@cnote/db` and `@cnote/live-db` no longer fall back to a localhost URL in production. The buyer web additionally refuses to start without the legal-entity variables (`LEGAL_ENTITY_STRICT=false` opts out). Outside production the same checks only warn. Dev and e2e opt-outs are explicit and named (`ALLOW_OTP_ECHO_IN_PRODUCTION`).
4. **Client IP and OTP (H4, M6).** `clientIp()` honours `cf-connecting-ip` only with `TRUST_CLOUDFLARE=1` and otherwise counts `TRUSTED_PROXY_HOPS` entries from the right of `X-Forwarded-For`; the first (client-controlled) entry is never used. The OTP code is returned to the caller only when `OTP_DEV_ECHO=true`, the sender is the console one, and either `NODE_ENV` is not production or `ALLOW_OTP_ECHO_IN_PRODUCTION=1` (packages/identity/src/dev-echo.ts). A real sender with the flag never echoes.
5. **Identity (H2, M1, M4).** GSTIN verification proves ownership signals (registry status, name similarity, state, PAN) and never overwrites a declared name; borderline results go to staff review; a squatted GSTIN is released only to a verified, name-matching claimant. Phone OTP sign-in runs the MFA gate and is refused for the admin realm. Linking Google to an unverified-email account revokes its sessions. Sign-up and reset do not reveal whether an email exists; account emails are enqueued on `identity.mail`, which makes the **worker a required process**.
6. **Deterministic moderation before the LLM (H3).** Every `<user_input>` envelope escapes `<`, `>` and `&`. `ai.moderate()` runs a keyword/regex pre-check over normalised text (zero-width stripped, homoglyph fold, leetspeak, spaced letters, Hinglish and Devanagari) before the model and merges the two verdicts by strictness: **the model may escalate, but a deterministic block or review is never relaxed to allow.** The golden set carries injection canaries. This is the implementation of ADR-008's requirement that AI decisions are bounded and auditable.
7. **Auto-approval needs more than the model (H3).** A listing is auto-approved only if the pre-check is clean AND the model allows AND tier/trust AND account age (`LISTING_AUTO_APPROVE_MIN_ACCOUNT_AGE_DAYS`, 30) AND staff-approved history (`LISTING_AUTO_APPROVE_MIN_HUMAN_APPROVED`, 3). **A random 5% sample (`LISTING_AUTO_APPROVE_SAMPLE_RATE`, 0.05) of auto-approvals also lands in the ops queue for post-publication audit**, so a bypass of the first layers is eventually seen by a human. The rate is a starting point to tune from review outcomes.
8. **Bounded inputs.** Server actions are capped at 2mb; forms with files post to route handlers that authenticate first and use `readBoundedFormData` (origin check, Content-Length cap, cap on received bytes). Archives are inflated under a streaming byte budget (zip/xlsx bombs). Exports neutralise spreadsheet formulas. Outbound fetches to user-supplied hosts resolve DNS once, refuse private ranges and connect to the validated IP (`assertPublicHttpTarget` + `pinnedFetch`). PII redaction regexes are bounded and input is capped at 20k characters.
9. **Business-logic abuse (M2, M3, M7).** A per-seller lead-refund guard routes excess `buyer_fake` reports to a staff queue instead of an instant refund (ADR-002's 72h refund remains for ordinary cases); coupons are reserved at checkout and redeemed inside the fulfilment transaction; message-email floods are coalesced; enquiry posting is limited per business, person and IP; domain claims are not globally unique, expire, and the first DNS-verified claimant wins.
10. **DPDP export and erasure (M10).** `/account/export` is assembled from a registry of per-module `exportPersonalData` sources, bounded by rows and bytes and streamed; UI erasure requires a step-up (password, MFA code or a fresh OTP).
11. **Supply chain.** GitHub Actions are pinned by SHA, Docker base images by digest, compose ports bind to loopback, Redis requires a password in dev compose, DB URLs reach `next build` as a BuildKit secret, and live AI evals run only in the protected `ai-evals` environment (ADR-043).

**Rationale.**
- Failing at boot is cheaper than discovering a missing webhook secret or plaintext database link in an incident.
- Triggers keep the ledger and consent guarantees true for the worker, scripts and future modules, not only for code that remembers the convention.
- A model that can only escalate makes prompt injection a nuisance (extra review) instead of a bypass.
- A regression test per control, named in the PRs, keeps the controls from decaying.

**Consequences.**
- Production needs a longer, explicit configuration (see `docs/ops/production-checklist.md`); a deploy with a missing item does not start.
- Dev setups that use the mock escrow or credit partner must set the webhook secrets in `.env.local`; existing test databases need `pnpm db:test:prepare` again.
- Deterministic keyword lists need upkeep and will produce false positives that go to review rather than block.
- The 5% audit sample consumes ops capacity.
- Residual risks the audit accepted or left open: the CSP still allows `unsafe-inline` on static pages (hash-based CSP is not feasible on Next 16); TOTP is phishable (passkeys are the next step for admin); the local key ring keeps key-encryption keys in env; moderate `uuid` advisory via `exceljs` (only `v4` is used); the MinIO images are pinned by tag, not digest (`TODO(supply-chain)`); proof of control of a GSTIN (taxpayer OTP) still needs a GSP/KYC vendor in production.
- Actions that cannot be done from code: create the `ai-evals` GitHub environment with required reviewers, lock the origin to Cloudflare, and optionally run the apps under the least-privilege DB role.

**Review.** After each external audit or incident, and when a new webhook provider, ledger table or AI capability is added (each needs its fail-closed secret check, trigger, or deterministic pre-check respectively).
